## Personal tenancy

`user` is the Better Auth source of truth and the billing subject. Custom user profile tables and
organization tables are intentionally absent. Project, Purchase, Credit Account, and Credit
Transaction rows are directly owned by a user and cascade appropriately.

## Provider-neutral billing

`@repo/billing` exposes a `BillingClient` and capability flags. Stripe and Polar adapters remain
private, and one deployment enables one provider. Pages branch on capabilities such as portal or
restore support instead of scattering provider names through the UI. Provider Product/Price
identifiers are configuration inputs; Provider webhooks remain the accounting authority.

## No background jobs

Email is awaited in the request that needs it. Auth email failures fail the auth request. Receipt
and payment-failed billing notices are auxiliary and isolated after committed facts. The exported
`sendWelcomeEmail` is currently only a generic compatibility extension point: no welcome template
or product flow calls it, and a direct call inherits the generic sender's default failure
propagation. Webhook processing is synchronous and returns a non-2xx response when its transaction
fails, allowing the Provider's own redelivery protocol to act. There is no internal queue, worker,
cron, outbox, or retry loop.

## Application-level authorization

The DB package exposes user-scoped query primitives but does not decide whether the caller is
authorized. `requireUser`, `requireAdmin`, and the action clients establish the trusted actor;
queries include that user id in SQL. This preserves an auditable authorization boundary without
introducing PostgreSQL RLS or a generic policy framework.

## Generated versus owned schema

`packages/db/src/schema/core.ts` is generated by the Better Auth CLI and must not be edited. Owned
tables live in `schema/billing.ts` and `schema/example.ts`. Billing does not create mirror
Subscription, Customer, Product, Price, or Entitlement tables. The database only persists the
minimum local facts needed for Credits, Lifetime purchases, and webhook idempotency.

## Source of truth for contracts

| Contract | Authoritative location |
| --- | --- |
| Package public API | `package.json` `exports` plus public barrel |
| Server/client environment | `packages/config/src/env/*` Zod schemas |
| Product and provider IDs | `packages/billing/src/config/billing-catalog.ts` |
| Better Auth core tables | generated `packages/db/src/schema/core.ts` |
| Product routes and actions | `apps/web/app/[locale]` |
| Repository architecture decisions | root `docs/architecture` and `docs/adr` |

This English documentation explains the contract for product users. It does not replace the
Chinese repository architecture documents, which remain the detailed implementation reference.
