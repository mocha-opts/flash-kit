# @repo/db

## Responsibility and non-goals

`@repo/db` owns the postgres.js/Drizzle client boundary, schema exports, migrations, grouped
query entry points, and database test helpers. It provides the process-wide default client,
isolated client creation, transaction support, Better Auth core schema, and the PII-free billing
Event ledger plus minimal user-owned Purchase persistence boundary.

It does not own Auth or Billing workflows, run migrations during application startup, or
implement a generic repository layer. The removable Project example lives in the `example`
schema and query subpath so it can be removed without changing Better Auth's generated core.

## Dependencies

Allowed dependencies: Drizzle ORM/Kit, postgres.js, `server-only`, `@repo/config`, the Better
Auth CLI for schema generation, and type/build tooling.

Forbidden dependencies: `@repo/auth`, `@repo/billing`, `@repo/email`, UI packages, provider
SDKs, and app internals. Auth may depend on DB; DB must never reverse that dependency.

## Public exports

| Export | Target | Purpose |
| --- | --- | --- |
| `@repo/db/client` | `src/client/index.ts` | Default/isolated Drizzle clients and transaction helpers. |
| `@repo/db/schema` | `src/schema/index.ts` | Server-only Better Auth and removable custom schema exports. |
| `@repo/db/queries/users` | `src/queries/users/index.ts` | User-scoped Better Auth profile/session queries and the explicit Admin user-list query boundary. |
| `@repo/db/queries/billing` | `src/queries/billing/index.ts` | Billing identity plus atomic Purchase/Event persistence primitives; no Billing workflow. |
| `@repo/db/queries/example` | `src/queries/example/index.ts` | User-scoped Project CRUD queries. |
| `@repo/db/testing` | `src/testing/index.ts` | Test-only database context boundary. |

## Minimal usage

```ts
import { db, withTransaction } from '@repo/db/client';
import { project } from '@repo/db/schema';
import { listProjectsForUser } from '@repo/db/queries/example';

async function loadProjects(session: { user: { id: string } }) {
  return await listProjectsForUser({
    userId: session.user.id,
    page: 1,
    limit: 25,
    status: 'all',
  });
}

await withTransaction(db, async (transaction) => transaction.select().from(project));
```

Use `createDatabaseClient()` for tests, scripts, or deployments that need an isolated pool.

## Placement rules

`src/schema/core.ts` is generated by the Better Auth CLI and must not be edited manually. Put the
removable Project table and its Project→User relation in `src/schema/example.ts`, and keep
reusable named queries under `queries/example/`. Keep client construction in `client/`; do not
add table-per-class repositories. Production code must not import `@repo/db/testing`.

## Security and transaction notes

Every runtime export is server-only. The default client is a Node-process singleton configured
by `DATABASE_URL` and `DATABASE_POOL_MAX`, with prepared statements disabled for transaction
pooler compatibility. User-scoped queries must include a trusted `userId` predicate. DB exposes
transaction mechanics and small feature queries only; atomic credit and billing workflows belong
to `@repo/billing`.

### Billing Purchase/Event query boundary

`@repo/db/queries/billing` exposes the database primitives used by `@repo/billing` to compose a
webhook transaction. The provider adapter first calls `upsertBillingEvent(db, input)` in a short
operation, then calls `claimBillingEvent(transaction, identity)` inside the business transaction.
The claim locks the row and returns `shouldProcess: false` for `processed` or `ignored` events.

```ts
await upsertBillingEvent(db, {
  provider: 'stripe',
  providerEventId: event.id,
  eventType: event.type,
});

await withTransaction(db, async (transaction) => {
  const claim = await claimBillingEvent(transaction, {
    provider: 'stripe',
    providerEventId: event.id,
  });

  if (!claim.shouldProcess) return;

  const result = await insertBillingPurchase(transaction, purchaseInput);
  if (result.inserted) {
    // Granting a Lifetime/Credit entitlement belongs to @repo/billing.
  }

  await markBillingEventProcessed(transaction, claim.event.id);
});
```

`markBillingEventProcessed`/`markBillingEventIgnored` must be called in the same transaction as
business writes. If that transaction fails, callers can use
`markBillingEventFailed(db, { provider, providerEventId, errorCode, errorMessage })` in a short
independent operation before rethrowing. The failure API accepts only a bounded, normalized error
category/message; it does not accept raw payloads, Error objects, stack traces, or user fields.
Callers must pass a safe, non-PII message. `insertBillingPurchase` relies on the unique
`(provider, provider_order_id)` index and returns `inserted: false` for duplicate orders.
`getActiveLifetimePurchaseForUser` returns only a paid Lifetime purchase; refunds and disputes do
not grant an Active Plan.

Refund/dispute composition uses the user-scoped `lockBillingPurchaseForUserByProviderOrder` and
`transitionBillingPurchaseStatus` primitives. Both the lock and guarded update include the trusted
`userId`, provider, provider order id, Purchase id, and expected status in SQL; a missing or
cross-user order is therefore indistinguishable from a missing order. The query layer does not
decide refund/dispute policy or append compensating Credit entries; those decisions belong to
`@repo/billing`.

`findCreditPurchaseGrantForUser` reads the immutable positive `purchase` transaction attached to a
Credit Pack. Billing uses this historical row—not the current Catalog—to calculate one full refund
compensation inside the caller-owned transaction. The original grant remains append-only, and the
Credit Account may become negative.

### Billing identity query boundary

`@repo/db/queries/billing` exposes only the minimum user-scoped identity fields required by the
Billing adapter (`id`, `name`, `email`, verification state, and the persisted Stripe customer id),
plus an atomic conditional write for an empty customer-id slot. It does not create customers,
start checkout, read Provider subscriptions, process webhooks, or own any Billing workflow; those
responsibilities remain inside `@repo/billing`.

### Admin user listing

`listUsersForAdmin(filters)` is the public Admin user-list query exported from
`@repo/db/queries/users`. The caller must complete a real Admin authorization check immediately
before calling it; the DB package does not authorize the caller. It supports bounded offset
pagination (`limit` 1–100, `offset` >= 0), case-insensitive name/email search, exact Admin/user
role filters (including comma-separated Better Auth roles), and active/banned status filters. The
query returns the total count with the page and classifies each role as `admin` or `user`.

Database errors from this query propagate to the caller. Do not replace it with Better Auth's
`listUsers` API, whose adapter error handling can turn a database failure into an empty result.

## Removing the Project example manually

The Project feature is intentionally removable. This is a manual checklist, not an automatic
deletion script. Before removing it, search the repository for `projects`, `project`, and
`@repo/db/queries/example` so product-specific callers are migrated first.

1. Remove the Web route directory `apps/web/app/[locale]/(app)/projects/`, including its Server
   Components, route-local loader, forms, actions, schemas, error boundary, and date helper.
2. Remove the Projects link from
   `apps/web/app/[locale]/(app)/_components/app-navigation.tsx`, then remove the matching
   `projects` namespace and `appNav.projects` key from both English and zh-CN message files.
3. Remove `packages/db/src/schema/example.ts` and its `export * from './example'` line from
   `packages/db/src/schema/index.ts`. Do not touch `packages/db/src/schema/core.ts`: it is
   generated by Better Auth and is not part of the removable example.
4. Remove `packages/db/src/queries/example/project.queries.ts` and its exports from
   `packages/db/src/queries/example/index.ts`. If the subpath has no remaining callers, remove
   the `./queries/example` entry from `packages/db/package.json` as well.
5. Remove the `./src/schema/example.ts` entry from `packages/db/drizzle.config.ts`. Remove the
   `@repo/db` dependency from `apps/web/package.json` only after a repository search confirms
   that Web has no other `@repo/db` imports; then refresh the lockfile with the normal package
   manager command.
6. Handle migration history according to deployment state. Before any migration is applied to
   a shared or deployed database, review the generated migration and snapshot changes together.
   After a migration has been applied, never edit or delete that migration or its journal entry.
   For an already deployed database, remove the table only through a new forward migration that
   contains the reviewed `DROP TABLE project` operation, then deploy that migration separately.
   Do not add a down-migration or run migrations automatically during build/startup.

After the checklist, run the package and Web typechecks, formatting/lint gates, and a production
build. Keep the historical migration files that have already been applied, and verify no import
or route still references the example.
